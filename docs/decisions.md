# Decisions

## A worker loop for N identical processes

### Context

Applications want to run N identical PHP processes (Supervisor `numprocs`, Kubernetes `replicas`) and scale by changing only that number.
`wwwision/subscription-engine` 2.x provides the primitives: `catchUpNextActive()` and `bootNext()` claim one subscription with `SKIP LOCKED`, `limit` bounds a batch, and failed runs are set aside per engine instance. What is missing is the loop around them.

### Decisions

| # | Topic | Decision | Why |
|---|-------|----------|-----|
| 1 | Package | New package `wwwision/subscription-engine-worker`. Requires core `^2`, `psr/log`, `psr/clock`. Suggests `ext-pcntl`. No DBAL at runtime. Can't be released before core 2.0 is tagged | Signals and process lifecycle are not the concern of core, which has only `psr/log` as dependency |
| 2 | What the loop runs | Each cycle calls `bootNext()` and then `catchUpNextActive()`, with `limit: 500` by default and the engine's order (lowest position first). Never `setup()` or `reset()` | Alternating keeps a long boot from starving active subscriptions, and the reverse. Concurrent `setup()` calls can fail with a duplicate key during discovery, so it is a deploy step. `NEW` subscriptions wait for it |
| 3 | Entry point | Library only: `Worker::run(): StopReason`, and a copyable `examples/worker.php`. No binary and no `symfony/console` | A generic binary can't build the subscribers of an application without a bootstrap file anyway. Framework commands can wrap the library |
| 4 | Forking | No `pcntl_fork` supervisor | It inherits open PDO connections and duplicates restart logic that Supervisor and Kubernetes already have |
| 5 | Waiter | `Waiter::wait(float $timeoutSeconds): void`. The package ships `SleepWaiter` and `CallbackWaiter`, there is no LISTEN code | `EventStoreWaiter` of `wwwision/dcb-eventstore-doctrine` already covers LISTEN, reconnects and channel naming: `new CallbackWaiter($eventStoreWaiter->waitForNewEvents(...))`. A generic LISTEN waiter would duplicate that and still need someone to send NOTIFY |
| 6 | Next step after a cycle | Pending events: `wait(0.0)` to drain, then continue. All locked: `wait(0.0)` to drain, then sleep 100 to 500 ms with jitter, without the waiter. Idle: `wait(maxIdleWait)`, by default 30 seconds. Always claim afterwards, the reason for a wake-up is ignored | Undrained listeners fill the notification queue of PostgreSQL, and appends fail once it is full. The short sleep lets extra workers claim soon after a lock is released, no notification would tell them. Always claiming covers the lock of a killed worker and the rare wrong `hasPendingEvents` |
| 7 | Signals | SIGTERM and SIGINT with `pcntl_async_signals` only set a flag. It is checked after each batch, and ends a wait early. Handlers are installed during `run()` and restored afterwards. Without `ext-pcntl`, `run()` throws unless `handleSignals: false`. A second signal does nothing special | SIGKILL is safe, the transaction rolls back, so a forced exit needs no code of its own |
| 8 | Other stop conditions | `maxRuntime`, `maxIterations` and `memoryLimit`, all off by default, all a regular return of `run()`. One iteration is a catch-up call that processed events. `maxRuntime` gets up to 10% of jitter and shortens waits. `memoryLimit` is checked after a batch | Idle wake-ups must not use up iterations. Without jitter, replicas recycle together. A check only after batches means that a worker starting above the limit doesn't restart in a loop, and that a batch can overshoot |
| 9 | `ERROR` subscriptions | Never retried automatically. The worker logs a warning with the affected subscriptions at startup and every 5 minutes | A retry would reapply an event that may be partially applied, and retry a poison event forever. A manual `SubscriptionEngine::retry()` that keeps the position would be a separate feature of core |
| 10 | Backoff for failed runs | Exponential per subscription, 1 to 60 seconds with ±20% jitter, kept in memory. The worker leaves the subscription out through `SubscriptionEngineCriteria` until the delay expires. `CatchUpFinished` clears it. An idle worker repeats a cycle once as soon as a delay has expired | With the set-aside of core alone, the retry rate follows the wake-up rate, so constant appends repeat a failing batch in a hot loop. The narrowed criteria let healthy subscriptions continue. The extra cycle is required because the engine clears its set-aside only in an idle run, the retry would otherwise wait for the next wake-up |
| 11 | Lost connections | An `Exception` escaping the engine or the waiter: call the optional `recover` callable, back off 1 to 30 seconds with ±20% jitter, and try again. After 5 minutes without a fully successful cycle, `run()` throws `WorkerFailed`. A PHP `Error` escapes right away. `recover` is also called after each failed run | Crashing right away could put Supervisor into `FATAL` during a short database restart. PDO can't reliably tell a lost connection from other errors, and closing a DBAL connection is safe and resets its nesting level |
| 12 | Observability | PSR-3 logs of start, stop reason, backoff and recovery. Passing a logger also logs engine events with their `logLevel()`. `onHeartbeat` is called every cycle. No metrics library | Core has no logger for its events. A heartbeat allows a Kubernetes exec probe to detect a worker that hangs on a half-open connection |
| 13 | Scaling metric | Documented SQL that returns the number of subscriptions that are behind, with `targetQueryValue: 1`. It counts `BOOTING`, and `ACTIVE` more than 100 events behind. `ERROR` is excluded. A test runs the exact query. `minReplicaCount: 1`, `maxReplicaCount` no higher than the number of subscriptions | A subscription runs on one worker at a time, so the count is the number of workers that can do work. A sum of events would start the maximum for a single lagging subscription. The SQL depends on the event store, and KEDA can only run SQL, so there is no PHP API |
| 14 | Meaning of "exactly once" | Asserted on committed rows of a projection with `UNIQUE(subscription, position)`, written through the connection of the store, not on handler calls | Handler calls legitimately repeat after a rollback. Handlers that write through another connection get at-least-once only |
| 15 | API | `new Worker($engine, $waiter, WorkerOptions::create(...), $logger)`. `run()` returns `StopReason` or throws `WorkerFailed`. Names follow core (`limit`). Delays are internal constants | Nothing asks to tune them so far, and they can become options without a break |
| 16 | Integration tests | Real worker processes, once with `SleepWaiter` and once with real LISTEN through `wwwision/dcb-eventstore-doctrine` `dev-main` | The only way to test the bridge and the drain against the real thing, at the cost of an unreleased dev dependency |
| 17 | Examples | Supervisor, Kubernetes `Deployment` and setup `Job`, KEDA `ScaledObject`, 60 seconds of grace period. A test checks that the YAML parses and that the settings stay aligned, nothing runs on a real cluster | 60 seconds assumes that a batch of 500 finishes well within that. Applications have to adjust it to their handlers |
| 18 | Core | No changes to core or adapters for this work. Tooling mirrors `wwwision/subscription-engine-doctrine` | Keeps this work additive |

### Known consequences

- **Workers beyond the number of subscriptions add no throughput.** They only find locked rows.
- **Backoff state is lost on restart and isn't shared.** N workers retry independently, so a failing subscription sees up to N retries per delay.
- **An error that repeats on PostgreSQL never leads to `ERROR`.** PostgreSQL ends the transaction for every SQL error, so the run fails and the subscription keeps its status. It is retried with backoff forever, only the logs show it. A persisted failure counter remains an open point of core.
- **A subscriber that was removed while another subscription is in backoff makes the narrowed call fail.** The engine rejects ids without a subscriber, and the worker has no way to list subscribers. The call is handled like a lost connection, and the removed subscriber is detached by the next call without a narrowed criteria.
- **The grace period has to exceed the worst-case batch.** Otherwise the process is killed, the batch is rolled back, and repeated by another worker.
- **A batch of external side effects can repeat.** See "exactly once" above.

### Known issues

**`DoctrineSubscriptionStore` can persist a position without its events after a lost connection.** DBAL closes the connection on its own if a statement reports a lost connection, which resets the nesting level. `assertTransactionIsIntact()` returns early if `isTransactionActive()` is `false`, so `update()` reconnects and writes the status and the position in autocommit, while the rows of the batch are gone. In a claimed run this results in `ERROR` at a position ahead of the projection. A blocking run updates its other subscriptions the same way, as `ACTIVE` at a position ahead of their projection. A handler that catches the exception itself has the same effect.

Reproduced by `workersRecoverIfTheirConnectionsAreTerminatedInTheMiddleOfABatch` against PostgreSQL 17: 7 of 8 runs failed. With a temporary change in the vendor copy, where the store remembers that it has begun a transaction and throws if DBAL has none anymore, 8 of 8 runs passed. This requires a fix in `wwwision/subscription-engine-doctrine`, the test stays red until then.
